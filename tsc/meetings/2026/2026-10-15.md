The group also talked about the potential for supporting in-memory textures to improve workflow integration with tools like Nuke and Houdini.

## Summary
### Modo and Foundry Connection Discussion:
The group discussed Modo and its connection to Foundry, with Duncan explaining that Foundry previously owned Luxology (which included Modo) but eventually discontinued it.
Rob mentioned recent MoonRay integration for Modo, including a GL preview that approximates MoonRay shaders.

### MoonRay Memory Management System:
Rob discussed implementing a memory management system for geometry source data in MoonRay, allowing users to control when data is deleted or moved to secondary storage
during rendering. He explained the current approach uses the scene data format to manage these objects, with an alternative design considered but deemed more complex to implement.
The system will primarily benefit users with tight memory constraints during batch renders, though it may also be useful internally. Rob also mentioned exploring the ability
to render from in-memory textures, as current support is limited to tile textures from files.

### Dynamic Textures in Rendering Workflows:
The team discussed the value and utility of dynamic textures in rendering workflows, particularly comparing approaches between Katana and Nuke. Duncan explained that Nuke's
dynamic texture generation through Hydra would be advantageous as it would be invisible to users compared to requiring disk exports as TX files. Rob described MoonRay's current
approach of using ARRAS with texture support, noting the challenge of transferring data between processes and the potential use of scene objects to store large blocks of binary data.

### Hydra Image and Texture Handling:
The team discussed Hydra's ability to handle images and textures, with Duncan explaining that USD has its own file loaders and an interface that provides pixel data through handles.
Rob questioned how these handles would be expressed in materials, noting that current textures are just file paths. The discussion concluded with Matthew bringing up a Slack
question about Metal 4 support, to which Michel explained that while there are some command queue processing changes in Metal, the benefits would be minimal as the current
implementation only involves a small setup cost. Michel indicated he would contribute the update if nobody else does, and clarified that there are no concerns about support
windows since Apple maintains older versions for years.

### MaterialX Support Implementation Update:
Paul explained his work on implementing MaterialX support in MoonRay, focusing on adding multiple output capabilities to address architectural omissions. He described the
technical challenges involved, including shader object classes and data structure modifications for handling multiple outputs. Paul outlined his approach of working through
tasks methodically in a separate project, with plans to submit pull requests as the work progresses through the internal review process.

### MaterialX Format Transition Discussion:
The team discussed transitioning from their current JSON format to MaterialX definitions for shader outputs, with Rob explaining that while MaterialX could accommodate
additional metadata, moving entirely to MaterialX would require addressing dependencies and standardizing metadata formats. The discussion revealed that Katana currently prefers
SDR definitions over pure MaterialX for UI population, though MaterialX definitions can be imported into SDR. The team also explored challenges with their current JSON format,
including order dependencies and the need for documentation

### Respository consolidation:
There was brief discussion around the benefits/drawbacks of consolidating the multiple repositories into a single repository for better CI management.
